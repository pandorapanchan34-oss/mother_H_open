## 1. 根本思想と基本大原則

> **根本思想**:
> **知能の独自性は守ってよい。しかし、安全を検証する権利と、自分の記憶を管理する権利は、決してブラックボックスの中に閉じ込めてはならない。**

自律AI「ぱんちゃん」およびその基盤 OS（Pankunn OS）を構築するにあたり、「利用者が安全性を第三者検証できる透明性」「独自の知能・製品価値の保護」「利用者個人の記憶・データの主権保護」の三者を両立させる必要がある。

本アーキテクチャでは、**カークホフスの原理（Kerckhoffs's principle）を設計上の基礎**とする。さらに、Pankunn OS 独自の公開原則として、**安全性の第三者検証に必要な機構・仕様・不変条件を公開し、安全性を秘密の実装に依存させない**ことを定める。

秘密にすべきものは、本番鍵・個人情報・運用秘密および独自の知能実装などに限定する。セキュリティ機構そのものを隠すことによって安全性を成立させる設計（Security through Obscurity）は採用しない。

## 2. 情報・コード・データの4分類モデル

Pankunn OS および Mother_H を構成する資産は、**コード・仕様・データ・鍵・運用情報などの管理単位ごとに分類**する。単一の機能やコンポーネントが複数領域にまたがる場合は責務を分離し、それぞれの境界を明示する。

| 分類 | 名称 | 公開方針 | 対象となる管理単位の例 |
| :--- | :--- | :--- | :--- |
| **A** | **完全公開（Open Source）** | 公開・第三者検証可能。一般に公開する資産には原則として Apache License 2.0（Apache-2.0）を採用 | 安全コア（FSM / Journal / ResourceGuard / PolicyEngine / AUTH-008・009 / Checkpoint・Recovery）、Execution Gateway 契約、Human Gate 安全仕様、公開プラグイン仕様 |
| **B** | **秘密情報として保護（Protected Secrets）** | 厳格秘匿（環境分離） | 本番署名鍵・MAC鍵・KEK、鍵の物理配置・運用手順、本番監査媒体の接続認証情報 |
| **C** | **独自技術として保護（Proprietary / Black Box）** | 非公開選択可。一般公開するコンポーネントには標準的なオープンソースライセンスまたは明確に定義された公開ライセンスを採用し、不明瞭な独自ライセンスの乱立を避ける | Pankunn Intelligence の独自推論・計画・状況認識エンジン、独自人格・対話モデル、独自最適化アルゴリズム |
| **D** | **個人ごとに隔離（Private User Domain）** | 利用者主権・暗号隔離 | 利用者自身の長期記憶、経験蓄積、価値観プロファイル、対話・判断履歴 |

### 領域 A（完全公開）が満たすべき公開要件

ソースコードを公開リポジトリに配置するだけでは第三者検証は成立しないため、領域 A の公開資産には以下の要素を伴わせることを要件とする。

- 領域 A（Mother_H 安全コア・公開 API 契約・Human Gate 安全仕様）の公開ライセンスは、原則として Apache License 2.0（Apache-2.0）を採用する。依存ライブラリのライセンス監査完了後に、リポジトリ直下へ `LICENSE` / `NOTICE` を配置する。
- ビルド・テストの再現手順
- テストの期待結果と実行前提・制約
- 既知の未実装事項および保証限界
- 依存ライブラリとそのライセンス一覧

> **評価の分離原則**: ソースコードや仕様を公開（領域 A に配置）した事実そのものは、安全性の証明を意味しない。**「公開されていること（Transparency）」「第三者が再現できること（Reproducibility）」「独立に検証されたこと（Independent Verification）」** は、それぞれ別の評価項目として区別して扱う。

> **重要原則（D領域の非企業秘密化）**: 利用者の記憶・価値観・判断履歴（領域 D）は、Pankunn OS の企業秘密（領域 C）として囲い込んではならない。利用者が自身のデータを閲覧・修正・エクスポート・消去できる主権を最優先する。

## 3. 採用する3つの基本方針と分類マトリクス

### 方針 ①：Mother_H の安全コアは原則すべて公開する（領域 A）

- 安全機構が、**定義された脅威モデルと保証範囲において、不正操作や権限逸脱をどのように拒否・制限するか**を、外部および利用者が検証可能にするため、`mother_H` の安全コアは原則すべて領域 A（Open Source）として公開する。
- **対象コンポーネント**: FSM・状態遷移検証、`Journal` / `JournalIntegrity`、`ResourceGuard`、`PolicyEngine`、`Execution Gateway` 契約、`AUTH-008` / `AUTH-009`、`Checkpoint` / `Recovery`、および `SIGNX` の公開仕様・検証インターフェース。
- **公開ライセンス**: 領域 A（Mother_H 安全コア・公開 API 契約・Human Gate 安全仕様）は、原則として Apache License 2.0（Apache-2.0）を採用する。依存ライブラリのライセンス監査完了後に、リポジトリ直下へ `LICENSE` / `NOTICE` を配置する。
- **留保事項**: `SIGNX` の具象実装については、対象コードおよび脅威モデルとの照合完了後に最終分類（A または C）を確定する。推測による分類確定は行わない。

### 方針 ②：Pankunn OS の AI 知能は「安全契約は公開（A）、独自エンジンは保護（C）」とする

- 上位知能層（JARVIS 型の状況認識、ドラえもん型の共存・対話設計、独自の計画・最適化エンジン等）は領域 C として独自実装を保護できる。
- ただし、知能層が安全コア（Mother_H）および外部世界と接続するための**公開 API 契約・プラグイン仕様・Human Gate 安全仕様**は必ず領域 A に配置し、独自エンジンであっても公開契約の範囲内でのみ動作するよう強制する。
- 領域 C のコンポーネントは非公開（Proprietary / Black Box）として保護できる。一方、一般公開するコンポーネントには標準的なオープンソースライセンスまたは明確に定義された公開ライセンスを採用し、不明瞭な独自ライセンスの乱立を避ける。

### 方針 ③：ユーザーの記憶・個人データは「ローカル保存を基本（D）」とし、外部同期は本人の明示選択制とする

- 個人データ（領域 D）は利用者が管理するローカル環境への保存を基本とする。
- クラウド同期や外部ストレージへの複製はデフォルト無効とし、利用者の明示的な選択と `AUTH-008` / `AUTH-009` 等の単回・範囲限定認可を経た場合に限り許可する。

### 対象別の分類方針一覧

| 対象 | 分類 | 方針 |
| :--- | :--- | :--- |
| Mother_H 安全コア | **A** | 原則公開 |
| SIGNX 具象実装 | **未確定** | 脅威モデルとコードの照合後に決定（仕様・検証IFは A） |
| API・プラグイン契約 | **A** | 公開 |
| Human Gate 安全仕様 | **A** | 公開 |
| Pankunn 独自知能エンジン | **C** | 保護可能 |
| 本番鍵・運用秘密 | **B** | 厳格秘匿 |
| ユーザー記憶・価値観 | **D** | 利用者主権（ローカル保存基本） |
| 個人データの暗号化外部同期 | **D** | 明示選択制（デフォルト無効） |

## 4. 追加制約条件（必須設計要件）

上記 3 方針を実効あるものとするため、以下の 4 要件をアーキテクチャ上の必須境界として課す。

### 条件 1：AI 知能の内部非公開と、外部操作に関する説明責任の公開（Explainable Safety Boundary）

独自知能エンジン（領域 C）の内部推論過程、モデルの重み、非公開のプロンプト戦略まで公開する必要はない。ただし、外部操作や状態変更を伴う要求が安全境界（Policy / Human Gate / Execution Gateway）を通過する際には、**少なくとも以下の説明可能な情報を構造化された公開フォーマットで提出・記録しなければならない**。

1. **目的と実行理由（Purpose & Rationale）**: 何を達成するためにその操作を行おうとしているか
2. **判断に使用した情報の出所（Information Provenance）**: 判断の根拠となった入力・参照データの出所
3. **確認できた事実（Verified / Observed Facts）**: システム上確認できている前提事実
4. **未確認の前提（Unverified Assumptions）**: 確認できていない仮定・不足情報
5. **不確実性とリスク・影響範囲（Uncertainty, Risk & Blast Radius）**: 操作対象、想定される不可逆的・外部的影響、失敗や誤判断のリスク
6. **代替手段（Alternatives）**: 他の選択肢やより影響の小さい手段の有無

さらに、Mother_H が機械的に検証できるのは権限・対象・承認状態・記録などの形式条件であり、AI が述べる動機や説明の真実性まで必ず検証できるわけではない。したがって、以下を厳格に区別する。

- **検証済みの事実と、AI が提示した説明・推定・主張は、決して同一視しない。** AI の自己申告はデータ構造上 `Unverified Claims` として扱い、それ単独を安全性の証拠や承認条件の充足根拠に用いない。

### 条件 2：承認と実行の一致、およびリプレイ・TOCTOU 対策

「過去に承認済みであること」と「今この瞬間に実行してよいこと」は明確に別個のものとして扱う。古い承認の再利用（リプレイ攻撃）や、承認後から実行開始までの状態変化（TOCTOU: Time-of-Check to Time-of-Use）を防ぐため、以下を必須要件とする。

- **一意な承認結合**: 承認と実行要求を一意の承認 ID（Grant / Approval ID）で厳密に結び付ける。
- **正規化による対象固定**: 対象リソース・操作種別・パラメータ・権限上限を正規化符号化して承認対象を固定し、実行要求と完全に一致しなければ Execution Gateway で無条件に拒否する。
- **有効期限の強制**: すべての承認に有効期限（TTL / Expiry）を設け、期限切れの承認は失効扱いで拒否する。
- **単回消費・二重実行防止**: 承認の再利用および並行・二重実行を永続的な状態遷移（`AUTH-008` / `AUTH-009` の消費・開始線形化点）によって遮断する。
- **状態変化時の再検証・再承認**: 承認後に対象リソースの状態、環境条件、または前提ポリシーが変化した場合は、既存の承認をそのまま適用せず再検証または再承認を要求する。
- **実行開始時の再確認と原子的競合制御**: 承認取得時だけでなく、実際の実行開始直前（`begin_execution` 時点）にも権限・取消状態・有効期限・対象一致を再度検証する。さらに、**実行開始時の再確認と実際の操作の間に競合状態が発生しないよう、対象リソースの特性に応じて原子的な条件付き実行、バージョン照合、ロックまたは同等の競合制御を適用する。** これらの制御で防止できない競合や、対象システム側に必要な原子性が存在しない場合は、その制約を明示し、安全に実行できない操作を拒否または保留する。

### 条件 3：Human Gate の独立した表示・承認経路（人間の意思決定保護）

AI が生成した説明文や緊急性の演出によって人間の判断が誘導されることを防ぐため、Human Gate は AI 知能層（領域 C）から独立した表示・承認経路を持たなければならない（将来の `HUMAN-001` 研究・設計項目の境界定義）。

- **安全コア主導の表示**: 操作対象・操作内容・権限上限・不可逆性などの重要情報は、AI の要約文ではなく安全コア（Mother_H）側で検証・正規化した情報から直接表示する。
- **視覚的・構造的区別**: AI が提示した説明文・推定と、システムが検証済みの事実情報を明確に区別して表示する。
- **権限分離と改ざん防止・検知**: AI 知能層から承認画面・承認履歴・承認結果への変更権限を分離し、不正な変更を防止または検知できる構造とする。保証範囲および信頼する実行環境は別途明示する。
- **選択の自由の確保**: 「承認」だけでなく、「拒否」「保留」「取消」「条件変更」の選択肢を常に明瞭に提供する。
- **誘導設計の禁止**: 不当な緊急性の演出、デフォルト承認への誘導、その他人間の冷静な拒否判断を妨げる UI / UX 設計を認めない。

### 条件 4：D 領域（個人データ）における「削除」と「復旧不能化」の3状態分離

領域 D の削除権および暗号消去（Cryptographic Shredding、`JOUR-010` / KEK-DEK 連携）においては、「ローカルで鍵を破棄したこと」を「すべての複製が物理的に消去されたこと」と同義に扱ってはならない。誤認を防ぐため、少なくとも以下の **3つの状態を厳密に区別して管理・表示** する。

| 状態 | 意味と保証範囲 |
| :--- | :--- |
| **1. 削除要求済み（Deletion Requested）** | 利用者が対象データの削除を要求し、削除・失効プロセスが開始された状態。データや鍵がまだ残存している可能性がある。 |
| **2. ローカル復号不能（Locally Unrecoverable）** | ローカルストアの DEK 破棄および失効アンカー更新により、ローカル環境では復号できなくなった状態。ただし、外部同期先やバックアップ媒体に複製が残存している可能性を排除しない。 |
| **3. 全追跡対象の削除・暗号消去確認済み（All Tracked Targets Deletion or Cryptographic Erasure Verified）** | 削除処理開始時点および処理中に追跡対象として登録されたローカル複製・キャッシュ・バックアップおよび許可済み外部同期先のすべてについて、データ本体の削除または当該複製を復号不能にする鍵の破棄・失効が確認できた状態。データ本体の削除と暗号消去は、実施内容と確認結果を区別して記録する。 |

- **対象範囲の明確化**: **「全追跡対象」とは、削除処理開始時点および処理中に追跡対象として登録された管理対象を指す。未把握の複製や、削除確認能力を持たない外部環境については、保証対象外または未確認として明示する。**
- **削除と暗号消去の区別**: データ本体の削除確認と、鍵の破棄・失効による暗号消去確認は別の結果として記録・表示する。鍵の破棄・失効はデータ本体の物理削除を意味しない。
- **必須設計要件と未確認時の扱い**: すべての複製について物理消去を無条件に保証するのではなく、**複製の追跡・鍵の分離・失効伝播・消去確認・残留リスクの明示** を必須とする。外部同期先やバックアップについて削除・失効の確認が取れない場合は、決して「全追跡対象の削除・暗号消去確認済み」と扱わず、未確認・残留可能性ありとして明示する。

※ 本3状態管理および複数複製・外部同期先の追跡フレームワークは、Pankunn OS 全体に向けた将来のアーキテクチャ設計要件であり、現行の Mother_H コードベースに実装・検証されているのはローカル DEK の破棄および失効アンカー更新（`JOUR-010` / KEK-DEK V1・V2）の範囲に限られる。

## 5. 絶対にブラックボックス化しない 7 原則（Non-Black-Box Invariants）

Pankunn OS および Mother_H において、いかなる拡張や製品化においても非公開化・隠蔽してはならない 7 項目を以下に定める。

1. **AI が何の権限を持つか**（Capabilities & Grants）
2. **どの条件で操作が許可・拒否されるか**（Policy Rules & Invariants）
3. **人間の承認が必要な操作は何か**（Human Gate Thresholds）
4. **どのような場合に Fail-Closed になるか**（Failure & Indeterminate Modes）
5. **AI が安全機構を無効化できない仕組み**（Anti-Tamper & Privilege Separation）
6. **記録・復旧・鍵管理の信頼境界**（Journal, Recovery & Key Trust Boundaries）
7. **安全性について何を保証していないか**（Explicit Non-Goals & Residual Risks）

## 6. 将来の論理構成案（Target Logical Architecture）と現行実装との境界

以下は将来の目標アーキテクチャを示す論理構成案であり、現行コードベースにおける実装済み機能や検証済みの保証を表すものではない。

|  Pankunn Intelligence [領域 C: 独自保護可]                        |
|  (推論・計画・状況認識・人格対話・最適化エンジン)                 |
+---------------------------------+---------------------------------+
                                  | 目的・出所・事実・未確認前提・リスク
                                  v (条件1: 自己申告と検証済み事実の分離)
+-------------------------------------------------------------------+
|  公開 API・プラグイン契約 / Human Gate 独立承認経路 [領域 A: 公開] |
|  (条件3: AI非依存表示・権限分離・拒否/保留保証・誘導禁止)         |
+---------------------------------+---------------------------------+
                                  |
                                  v
+-------------------------------------------------------------------+
|  Mother_H Security Core [領域 A: 完全公開（ライセンス・再現手順付）]|
|  (FSM / Policy / ResourceGuard / Journal / AUTH-008・009 /        |

                                  | 条件2: 一意ID・正規化一致・TTL・単回・
                                  | 状態変化再検証・実行開始時再確認/

                                  v
+-------------------------------------------------------------------+
|  Execution Gateway [領域 A: 契約公開]                             |
+--------+------------------------+------------------------+--------+
         |                        |                        |
         v                        v                        v
[Host OS / Hardware]    [領域 B: Protected Secrets]  [領域 D: Private User Domain]

### 現行実装との関係

- 本図は将来の論理的な責務分離と信頼境界を示すものであり、各コンポーネントが現行実装に存在することを保証しない。
- 実装の有無、テスト状況、保証可能な範囲は、現行の正式計画および進捗・完了状態文書に基づいて別途確認する。
- 本 ADR の採択によって、未実装機能が実装済みとみなされたり、未検証の保証が成立したりすることはない。
